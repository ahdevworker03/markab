## 1. Purpose

This document separates the currently implemented PostgreSQL/Prisma model from approved target model changes awaiting implementation. Implemented fields and behavior describe the current runtime contract; target additions are explicitly marked and must not be treated as present until their schema, API, validation, and application work is completed.

## 2. Source of Truth and Scope

- Current Prisma schema: `lib/db/prisma/schema.prisma`.
- Implemented database constraints: `lib/db/prisma/migrations/`.
- Business meaning: `docs/product/04-domain-model.md` and `docs/product/02-business-requirements.md`.
- Backend and API conventions: `docs/architecture/04-backend-architecture.md` and `docs/architecture/06-api-design.md`.
- Prisma schema and applied migrations take precedence for implemented fields, enums, relations, indexes, and constraints. Product documents supply meaning; they do not add unimplemented persistence.
- The interval recurrence, recurrence end-condition, and `occurrence_number` fields in the Task section are approved target changes awaiting implementation; they are not currently present in the Prisma schema, migrations, API contract, generated clients, or runtime behavior.
- This document records completed backend state through Milestones 5.6 and 5.7 plus the approved target model. It does not authorize schema, migration, API, or product changes.

## 3. Shared Conventions

### 3.1 IDs, Names, and Audit Fields

- Model primary keys are `id: UUID`, generated by Prisma `uuid()` and stored as PostgreSQL UUIDs.
- Tables and columns use singular/lowercase and `snake_case`; foreign keys use `<entity>_id`; enum values use `UPPER_SNAKE_CASE`.
- Unless a model table says otherwise, `created_at` defaults to `now()` and `updated_at` uses `@updatedAt`.
- UUIDs support global identity and future offline synchronization. They carry no business meaning.

### 3.2 Tenant Isolation

- Tenant-owned records carry a required `organization_id` FK and must be queried and mutated only in the authenticated organization context.
- Organization identity comes from authenticated server context, never a client-provided organization ID.
- Related tenant records must belong to the same organization. Cross-tenant relationships are rejected by services even where a composite database FK is not present.
- `AuditLog` is exceptional: its organization and actor are optional so platform-level events can be recorded.

### 3.3 Soft Deletes

- Business models with `deleted_at` are soft-deletable. Normal reads, searches, derived balances, and reports exclude soft-deleted records unless an explicit historical/audit operation requires otherwise.
- Direct API retrieval of soft-deleted business/media records behaves as not found. Soft deletion preserves history and recovery data.
- `AuditLog`, `RefreshToken`, `PasswordResetToken`, and `EmployeeInvitation` do not use `deleted_at`; lifecycle is described by their fields or deletion workflow.
- Soft-deleting media does not itself delete the underlying storage object. Storage cleanup is a separate future concern.

### 3.4 Foreign Keys, Deletes, and Indexes

- Required business relationships use PostgreSQL foreign keys. Prisma relations without an explicit `onDelete` use the implemented default restrictive behavior; explicit exceptions are listed below.
- `RefreshToken.user_id` and `PasswordResetToken.user_id` use `CASCADE`; deleting a user removes those security tokens.
- All implemented indexes and unique constraints below are schema contracts. Indexes exist for FK lookup, soft-delete filtering, and documented operational searches.

### 3.5 Validation and API Boundaries

- Request validation checks required fields, types, formats, enum values, and ranges. Services enforce authorization, organization ownership, lifecycle transitions, and cross-record rules. The database enforces keys, FKs, unique indexes, and listed check constraints.
- Resources use plural lowercase `/api/*` paths. Successful responses are `{ "data": ... }`; errors are `{ "error": { "code": "...", "message": "..." } }`.
- Use `GET`, `POST`, `PATCH`, and soft-delete `DELETE` consistently. API definitions in `lib/api-spec` remain the public contract.

## 5. Core SaaS and Security Models

### 5.1 Organization

**Purpose:** Tenant business profile and ownership root.

**Relationships:** Has many users, customers, vehicles, rentals, contracts, documents, photos, maintenance records/schedules, expenses, payments, tasks, audit logs, and employee invitations.

| Field | Type | Required | Default | Notes |
|---|---:|---:|---:|---|
| `id` | UUID | Yes | `uuid()` | Primary key. |
| `name` | String | Yes | - | Operating business name. |
| `status` | `OrganizationStatus` | Yes | `TRIAL` | Tenant lifecycle. |
| `legal_name`, `phone`, `email`, `address`, `contract_footer_text` | String | No | `null` | Optional business identity/profile fields for contracts and reports. |
| `created_at`, `updated_at`, `deleted_at` | DateTime | Yes, Yes, No | shared | `deleted_at` soft-deletes the organization. |

**Constraints and indexes:** `@@index([deleted_at])`; names are not unique.

**Business rules and API notes:** Organization profile is available through `/api/organizations/me`. SaaS pricing, subscriptions, and billing are not represented here. Platform owners alone update another tenant's lifecycle status. Existing tenants were backfilled to `ACTIVE` when lifecycle support was introduced.

### 5.2 User

**Purpose:** Authenticated person belonging to one tenant.

**Relationships:** Belongs to one organization; has refresh tokens, password-reset tokens, audit logs, created invitations, and at most one accepted invitation relation.

| Field | Type | Required | Default | Notes |
|---|---:|---:|---:|---|
| `id` | UUID | Yes | `uuid()` | Primary key. |
| `email` | String | Yes | - | Globally unique login identity. |
| `password_hash` | String | Yes | - | Password hash only; never return it. |
| `role` | `Role` | Yes | `OWNER` | `PLATFORM_OWNER`, `OWNER`, or `EMPLOYEE`. |
| `organization_id` | UUID | Yes | - | FK to `Organization`. |
| `created_at`, `updated_at`, `deleted_at` | DateTime | Yes, Yes, No | shared | Deleted users cannot authenticate. |

**Constraints and indexes:** `@unique(email)`; `@@index([organization_id])`; `@@index([deleted_at])`.

**Validation/API notes:** Email must be valid; creation passwords require at least 8 characters; role must be valid. Registration creates an organization and an `OWNER`. Employee invitations create only `EMPLOYEE` users. User list/get is available to authenticated tenant users; management operations are owner-only under the implemented role policy.

### 5.3 RefreshToken

**Purpose:** Persisted session-continuation token hash.

**Relationships:** Belongs to one user; `user_id` cascades on user deletion.

| Field | Type | Required | Default | Notes |
|---|---:|---:|---:|---|
| `id` | UUID | Yes | `uuid()` | Primary key. |
| `token` | String | Yes | - | Unique SHA-256 hash of the opaque refresh token. |
| `user_id` | UUID | Yes | - | FK to `User`, `CASCADE` on delete. |
| `expires_at`, `created_at` | DateTime | Yes | - / `now()` | Expiry and creation time. |

**Constraints and indexes:** `@unique(token)`; `@@index([user_id])`; `@@index([expires_at])`.

**Business rules:** Persist only the hash; send plaintext once. Refresh rotation invalidates the previous token. Logout, expiry, or password reset revokes/deletes token records as applicable.

### 5.4 EmployeeInvitation

**Purpose:** Organization-scoped invitation for employee onboarding.

**Relationships:** Belongs to one organization; created by one user; may reference the user created on acceptance. All FKs use `RESTRICT`.

| Field | Type | Required | Default | Notes |
|---|---:|---:|---:|---|
| `id` | UUID | Yes | `uuid()` | Primary key. |
| `organization_id` | UUID | Yes | - | Tenant owner. |
| `email` | String | Yes | - | Invited email. |
| `token_hash` | String | Yes | - | Unique opaque-token hash; plaintext is never stored. |
| `expires_at`, `accepted_at` | DateTime | Yes, No | - / `null` | Expiration and single acceptance marker. |
| `created_by_user_id` | UUID | Yes | - | Inviting user. |
| `accepted_user_id` | UUID | No | `null` | Unique accepted user reference. |
| `created_at`, `updated_at` | DateTime | Yes | shared | Audit fields. |

**Constraints and indexes:** `@unique(token_hash)`; `@unique(accepted_user_id)`; `@@unique([organization_id, email])`; `@@index([organization_id, expires_at])`; `@@index([accepted_at])`.

**Business rules:** Invitations grant only `EMPLOYEE`. Resending replaces the earlier token hash and expiry for the organization/email record. Acceptance creates the user and marks the invitation accepted in one serializable transaction, preventing replay and concurrent double acceptance while retaining global user-email uniqueness.

### 5.5 PasswordResetToken

**Purpose:** One-time password reset credential.

**Relationships:** Belongs to one user; `user_id` cascades on user deletion.

| Field | Type | Required | Default | Notes |
|---|---:|---:|---:|---|
| `id` | UUID | Yes | `uuid()` | Primary key. |
| `token_hash` | String | Yes | - | Unique opaque-token hash; plaintext is never stored. |
| `user_id` | UUID | Yes | - | FK to `User`, `CASCADE` on delete. |
| `expires_at`, `consumed_at`, `created_at` | DateTime | Yes, No, Yes | - / `null` / `now()` | Expiry, consumption marker, creation. |

**Constraints and indexes:** `@unique(token_hash)`; `@@index([user_id, consumed_at])`; `@@index([expires_at])`.

**Business rules:** A new request invalidates the user's previous unused reset token. Confirmation consumes the valid token, replaces the password hash, revokes all refresh tokens, and writes an audit event in one serializable transaction.

### 5.6 AuditLog

**Purpose:** Append-only platform/security audit record, not event sourcing.

**Relationships:** Optionally belongs to an organization and actor user; both FKs use `RESTRICT`.

| Field | Type | Required | Default | Notes |
|---|---:|---:|---:|---|
| `id` | UUID | Yes | `uuid()` | Primary key. |
| `organization_id`, `actor_user_id` | UUID | No | `null` | Optional tenant and actor context. |
| `action`, `target_type` | String | Yes | - | Event action and target category. |
| `target_id` | String | No | `null` | Optional target identifier. |
| `metadata` | JSON | No | `null` | Non-sensitive structured metadata only. |
| `created_at` | DateTime | Yes | `now()` | Immutable event time. |

**Indexes:** `@@index([organization_id, created_at])`; `@@index([actor_user_id, created_at])`; `@@index([target_type, target_id])`.

**Business rules:** Records are retained, not soft-deleted through normal operations. Lifecycle status changes are audited in the same transaction; invitation, password-reset, and account-administration workflows use the same mechanism.

## 6. Core Business Models

### 6.1 Customer

**Purpose:** Rental customer identity, contact, and driver's-license record.

**Relationships:** Belongs to one organization; has rentals and documents.

| Field | Type | Required | Default | Notes |
|---|---:|---:|---:|---|
| `id`, `organization_id` | UUID | Yes | `uuid()` / - | Primary key and tenant FK. |
| `first_name`, `last_name`, `phone`, `address` | String | Yes | - | Required identity/contact data. |
| `national_id`, `license_number` | String | Yes | - | Tenant-unique identity/license values. |
| `license_expiry_date` | DateTime | Yes | - | Required license expiry. |
| `created_at`, `updated_at`, `deleted_at` | DateTime | Yes, Yes, No | shared | Archived customers are soft-deleted. |

**Constraints and indexes:** `@@unique([organization_id, national_id])`; `@@unique([organization_id, license_number])`; indexes on `organization_id`, `deleted_at`, `first_name`, `last_name`, `phone`, `national_id`, and `license_number`. Migration check constraint limits `license_expiry_date` to `1900-01-01` through `2100-12-31`.

**Business rules and validation:** Required strings are non-empty; license expiry is a valid supported date. Rental history is derived from rentals. Archived customers do not participate in new rentals. Customer search supports name, phone, national ID, and license number.

### 6.2 Vehicle

**Purpose:** Central business asset managed through rental, maintenance, media, and expense history.

**Relationships:** Belongs to one organization; has rentals, maintenance records/schedules, expenses, documents, and photos.

| Field | Type | Required | Default | Notes |
|---|---:|---:|---:|---|
| `id`, `organization_id` | UUID | Yes | `uuid()` / - | Primary key and tenant FK. |
| `make`, `model`, `plate_number`, `color` | String | Yes | - | Required vehicle identity/details. |
| `year`, `seats` | Int | Yes | - | Valid year and positive seat count. |
| `notes` | String | No | `null` | Optional general notes; non-empty when supplied. |
| `transmission`, `fuel_type` | Enum | Yes | - | `Transmission` and `FuelType`. |
| `current_mileage` | Int | Yes | `0` | Non-negative kilometers. |
| `status` | `VehicleStatus` | Yes | `AVAILABLE` | Current operational state. |
| `created_at`, `updated_at`, `deleted_at` | DateTime | Yes, Yes, No | shared | Archived vehicles are soft-deleted. |

**Constraints and indexes:** `@@unique([organization_id, plate_number])`; indexes on `organization_id`, `deleted_at`, `status`, `make`, `model`, and `plate_number`.

**Business rules:** A vehicle has no more than one active rental. Archived vehicles cannot enter new rentals. Lifecycle includes available, reserved, rented, maintenance, and archived states; sale-related lifecycle stages remain future work. Mileage uses kilometers only.

### 6.3 Rental

**Purpose:** Agreement assigning one vehicle to one customer for a defined period and price.

**Relationships:** Belongs to one organization, customer, and vehicle; has at most one contract and many payments.

| Field | Type | Required | Default | Notes |
|---|---:|---:|---:|---|
| `id`, `organization_id`, `customer_id`, `vehicle_id` | UUID | Yes | `uuid()` / - | Primary key and required FKs. |
| `pickup_date`, `expected_return_date` | DateTime | Yes | - | Agreed rental period. |
| `actual_pickup_date`, `actual_return_date` | DateTime | No | `null` | Recorded lifecycle moments. |
| `status` | `RentalStatus` | Yes | `RESERVED` | Reserved, active, returned, or cancelled. |
| `daily_rate`, `total_amount`, `deposit_amount` | Decimal | Yes | - | `Decimal(10,2)` financial snapshots. |
| `created_at`, `updated_at`, `deleted_at` | DateTime | Yes, Yes, No | shared | Historical soft delete. |

**Constraints and indexes:** indexes on `organization_id`, `customer_id`, `vehicle_id`, `status`, `pickup_date`, `expected_return_date`, `deleted_at`, and `@@index([vehicle_id, pickup_date, expected_return_date])`.

**Business rules and validation:** Customer and vehicle must be in the same organization. Pickup must precede expected return. The rental service prevents overlapping active/reserved bookings and rejects archived vehicles. Pickup activates a reserved rental; return records actual return; extension must preserve availability; cancellation releases the vehicle. Amounts use `Decimal(10,2)` and must follow the rental API validation contract.

### 6.4 Contract

**Purpose:** Immutable-at-generation rental agreement snapshot used for printing, PDF export, and signed-document storage.

**Relationships:** Belongs to one organization and one rental; has documents.

| Field | Type | Required | Default | Notes |
|---|---:|---:|---:|---|
| `id`, `organization_id`, `rental_id` | UUID | Yes | `uuid()` / - | Primary key and required FKs. |
| `pickup_date`, `expected_return_date` | DateTime | Yes | - | Rental-period snapshot. |
| `daily_rate`, `total_amount`, `deposit_amount` | Decimal | Yes | - | `Decimal(10,2)` financial snapshot. |
| `customer_first_name`, `customer_last_name`, `customer_national_id` | String | Yes | - | Customer identity snapshot. |
| `vehicle_make`, `vehicle_model`, `vehicle_plate_number` | String | Yes | - | Vehicle snapshot. |
| `created_at`, `updated_at`, `deleted_at` | DateTime | Yes, Yes, No | shared | Contract history soft delete. |

**Constraints and indexes:** `@@unique([rental_id])`; indexes on `organization_id`, `rental_id`, and `deleted_at`.

**Business rules:** One contract per rental. Contract snapshots retain the agreement facts even if customer or vehicle records later change. Contract documents are owned through `Document.contract_id`.

### 6.5 Payment

**Purpose:** Manual record of money already received by the rental business for a rental.

**Relationships:** Belongs to one organization and one rental.

| Field | Type | Required | Default | Notes |
|---|---:|---:|---:|---|
| `id`, `organization_id`, `rental_id` | UUID | Yes | `uuid()` / - | Primary key and required FKs. |
| `amount` | Decimal | Yes | - | `Decimal(10,2)`, strictly greater than zero. |
| `payment_date` | DateTime | Yes | - | When money was received. |
| `method` | `PaymentMethod` | Yes | - | Cash, card, transfer, or other recorded method. |
| `created_at`, `updated_at`, `deleted_at` | DateTime | Yes, Yes, No | shared | Deleted payments are excluded from balances/reports. |

**Constraints and indexes:** indexes on `organization_id`, `rental_id`, `deleted_at`, and `payment_date`; no unique rental constraint because partial payments are valid.

**Business rules and validation:** Rental must be in the same organization. A rental can have multiple recorded payments. Outstanding balance is derived as `Rental.total_amount` less valid recorded payments and is never stored on `Payment`. This is not online payment processing: it includes no Whish, QR, gateway, checkout, webhook, refund, chargeback, or payment-status concepts.

### 6.6 Expense

**Purpose:** Business cost that is optionally attributable to one vehicle.

**Relationships:** Belongs to one organization and optionally one vehicle; the optional vehicle FK uses `RESTRICT`.

| Field | Type | Required | Default | Notes |
|---|---:|---:|---:|---|
| `id`, `organization_id` | UUID | Yes | `uuid()` / - | Primary key and tenant FK. |
| `vehicle_id` | UUID | No | `null` | Optional vehicle FK. |
| `expense_date` | DateTime | Yes | - | Date incurred. |
| `amount` | Decimal | Yes | - | `Decimal(10,2)`, non-negative. |
| `category` | `ExpenseCategory` | Yes | - | Operational cost category. |
| `description` | String | No | `null` | Non-empty if supplied. |
| `created_at`, `updated_at`, `deleted_at` | DateTime | Yes, Yes, No | shared | Soft delete. |

**Constraints and indexes:** indexes on `organization_id`, `vehicle_id`, `category`, `deleted_at`, and `expense_date`.

**Business rules:** A supplied vehicle must share the tenant. No currency field is stored. Maintenance work is not an expense category or relationship: `Maintenance.cost` is the sole authoritative maintenance cost. Financial reporting avoids double-counting by summing other expenses separately from completed maintenance cost.

### 6.7 Maintenance

**Purpose:** Planned or performed vehicle maintenance and vehicle maintenance history.

**Relationships:** Belongs to one organization and one vehicle.

| Field | Type | Required | Default | Notes |
|---|---:|---:|---:|---|
| `id`, `organization_id`, `vehicle_id` | UUID | Yes | `uuid()` / - | Primary key and required FKs. |
| `type`, `status` | Enum | Yes | - / `SCHEDULED` | `MaintenanceType` and `MaintenanceStatus`. |
| `maintenance_date` | DateTime | Yes | - | Scheduled/due business date; actual work date for backfilled history. |
| `completed_at` | DateTime | No | `null` | Actual completion time. |
| `cost` | Decimal | No | `null` | `Decimal(10,2)` authoritative cost. |
| `vendor`, `notes` | String | No | `null` | Non-empty if supplied. |
| `replaced_parts` | JSON | No | `null` | Structured parts breakdown; `null` when empty. |
| `created_at`, `updated_at`, `deleted_at` | DateTime | Yes, Yes, No | shared | Soft delete instead of cancellation. |

**Constraints and indexes:** indexes on `organization_id`, `vehicle_id`, `deleted_at`, `status`, and `maintenance_date`.

**Business rules and validation:** `UPCOMING`/`OVERDUE` are derived from `maintenance_date` for non-completed records. `COMPLETED` requires `completed_at` and `cost`; unfinished records may leave cost null. `0.00` is a real zero-cost event, not an unknown-cost marker. `cost` is non-negative and is the sole financial total; `unitCost` in `replaced_parts` is informational and not separately aggregated. Each part has a non-empty `name`, optional `brand`, optional positive `quantity` (default 1), and optional non-negative `unitCost`. Vehicle status changes are workflow behavior, not a model side effect.

### 6.8 MaintenanceSchedule

**Purpose:** Active or paused future servicing rule for one vehicle; it is not a maintenance-work record.

**Relationships:** Belongs to one organization and one vehicle; both FKs use `RESTRICT`.

| Field | Type | Required | Default | Notes |
|---|---:|---:|---:|---|
| `id`, `organization_id`, `vehicle_id` | UUID | Yes | `uuid()` / - | Primary key and required FKs. |
| `maintenance_type` | `MaintenanceType` | Yes | - | Intended service category. |
| `schedule_type` | `MaintenanceScheduleType` | Yes | - | Date, mileage, or either basis. |
| `date_interval_days` | Int | No | `null` | Positive for date-capable schedules. |
| `next_due_date` | Date | No | `null` | PostgreSQL `DATE` business date. |
| `mileage_interval` | Int | No | `null` | Positive for mileage-capable schedules. |
| `next_due_mileage` | Int | No | `null` | Non-negative odometer threshold. |
| `is_active` | Boolean | Yes | `true` | Enables or pauses the rule. |
| `created_at`, `updated_at`, `deleted_at` | DateTime | Yes, Yes, No | shared | Soft-deletable schedule. |

**Constraints and indexes:** PostgreSQL `MaintenanceSchedule_schedule_basis_check` requires exactly the fields appropriate to the selected basis: `DATE` requires valid date values and null mileage values; `MILEAGE` requires valid mileage values and null date values; `DATE_OR_MILEAGE` requires both. Indexes: `organization_id`, `vehicle_id`, `deleted_at`, `is_active`, `next_due_date`, and `next_due_mileage`.

**Explicit exclusions:** A schedule does not create maintenance records, change vehicle status or availability, send notifications, run background jobs, or automate mileage updates. Those workflows remain deferred.

### 6.9 Task

**Purpose:** Tenant operational reminder, including basic recurring occurrences.

**Relationships:** Belongs to one organization; optionally references one predecessor task and can have at most one direct successor. The self-FK uses `RESTRICT`.

The recurrence interval, unit, end-condition, and occurrence-number fields below
are approved target fields awaiting implementation. They are not currently in
the Prisma schema or applied migrations.

| Field | Type | Required | Default | Notes |
|---|---:|---:|---:|---|
| `id`, `organization_id` | UUID | Yes | `uuid()` / - | Primary key and tenant FK. |
| `due_date` | DateTime | Yes | - | Due/business date. |
| `status` | `TaskStatus` | Yes | `PENDING` | Pending or completed. |
| `recurrence_interval`, `recurrence_unit` (approved target) | Int, enum | No, No | `null` / `null` | No recurrence when absent; otherwise a positive interval in days, weeks, or months. |
| `recurrence_end_date`, `recurrence_end_count` (approved target) | Date, Int | No, No | `null` / `null` | Optional end condition; at most one end condition is selected. |
| `occurrence_number` (approved target) | Int | Yes | `1` | Positive occurrence position; original task is 1. |
| `predecessor_id` | UUID | No | `null` | Unique FK to the immediate preceding occurrence. |
| `notes` | String | No | `null` | Non-empty if supplied. |
| `created_at`, `updated_at`, `deleted_at` | DateTime | Yes, Yes, No | shared | Soft delete. |

**Constraints and indexes:** `@unique(predecessor_id)` ensures a task has at most one direct successor. Indexes: `organization_id`, `deleted_at`, `status`, and `due_date`.

**Approved target business rules:** A task has no recurrence when its recurrence configuration is absent; otherwise the interval is positive and the unit is `DAY`, `WEEK`, or `MONTH`. Daily, weekly, and monthly presets use interval one. The end condition is never, an inclusive Beirut-local business date, or a positive occurrence count. "After N occurrences" includes the original task: the original is occurrence 1, so an end count of 5 permits at most four successors. `occurrence_number` starts at 1 and each successor receives its predecessor's number plus 1. Do not create a successor when the current occurrence has reached `recurrence_end_count`, or when the successor's Beirut-local business date would be after `recurrence_end_date`; equality is allowed. Completing the current recurring occurrence atomically preserves it as `COMPLETED` history and creates exactly one next `PENDING` occurrence when recurrence remains active and its end condition permits it. The successor copies notes and recurrence configuration. Its due date is calculated using `Asia/Beirut` business date/time semantics, including timezone transitions; persisted timestamps may remain UTC. Stopping recurrence preserves the current task and history and prevents future successors. Normal deletion soft-deletes only the selected occurrence by setting `deleted_at`; it is not whole-series deletion and does not hard-delete records. There is no background scheduler, notification delivery, complex recurrence syntax, or vehicle/rental/maintenance/user association.

## 7. Media Models

### 7.1 Shared Media Rules

- `Document` and `Photo` use explicit FKs, not polymorphic `entity_type + entity_id` ownership.
- `storage_key` is a globally unique, opaque server-generated storage reference and is never client supplied. A typical internal structure is `<organization_id>/<entity>/<uuid>.<extension>`; extensions derive from validated MIME type.
- Supported photo MIME types are `image/jpeg`, `image/png`, and `image/webp`. Supported document MIME types are `application/pdf`, `image/jpeg`, and `image/png`.
- Original filenames are required, non-empty, sanitized, and cannot retain path separators. File sizes are non-negative integers and limited to 10 MB by application validation.

### 7.2 Document

**Purpose:** File attached to exactly one vehicle, customer, or contract.

**Relationships:** Belongs to one organization and exactly one explicit owner: a vehicle, customer, or contract. Each owner FK uses `RESTRICT`.

| Field | Type | Required | Default | Notes |
|---|---:|---:|---:|---|
| `id`, `organization_id` | UUID | Yes | `uuid()` / - | Primary key and tenant FK. |
| `vehicle_id`, `customer_id`, `contract_id` | UUID | Individually no; collectively yes | `null` | Exactly one owner FK must be set. |
| `category` | `DocumentCategory` | Yes | `OTHER` | Registration, insurance, or other. |
| `expiry_date` | Date | No | `null` | PostgreSQL `DATE`; document expiry, not a timestamp. |
| `original_filename`, `mime_type` | String | Yes | - | Sanitized display filename and validated content type. |
| `file_size` | Int | Yes | - | Byte size. |
| `storage_key` | String | Yes | - | Unique server-generated storage reference. |
| `created_at`, `updated_at`, `deleted_at` | DateTime | Yes, Yes, No | shared | Soft delete. |

**Constraints and indexes:** `@unique(storage_key)`; PostgreSQL `Document_exactly_one_owner_check` requires exactly one of `vehicle_id`, `customer_id`, or `contract_id`; `Document_expiry_date_range_check` allows null or `1900-01-01` through `2100-12-31`. Indexes: `organization_id`, each owner FK, `category`, `expiry_date`, and `deleted_at`.

**Business rules and API notes:** The owner must belong to the document's organization. Vehicle/customer/contract document APIs operate through their owning resource. A document category describes the file, while expiry supports registration/insurance tracking. Signed contracts are contract-owned documents.

### 7.3 Photo

**Purpose:** Vehicle-only image attachment.

**Relationships:** Belongs to one organization and one vehicle.

| Field | Type | Required | Default | Notes |
|---|---:|---:|---:|---|
| `id`, `organization_id`, `vehicle_id` | UUID | Yes | `uuid()` / - | Primary key and required FKs. |
| `sort_order` | Int | Yes | `0` | Ascending display order. |
| `caption` | String | No | `null` | Non-empty if supplied. |
| `original_filename`, `mime_type` | String | Yes | - | Sanitized filename and validated image type. |
| `file_size` | Int | Yes | - | Byte size. |
| `storage_key` | String | Yes | - | Unique server-generated storage reference. |
| `created_at`, `updated_at`, `deleted_at` | DateTime | Yes, Yes, No | shared | Soft delete. |

**Constraints and indexes:** `@unique(storage_key)`; indexes on `organization_id`, `vehicle_id`, `@@index([vehicle_id, sort_order])`, and `deleted_at`.

**Business rules:** The vehicle must share the photo's organization. Lowest `sort_order` is the display-first photo; no separate primary-photo boolean exists.

## 8. Reporting and Derived Concepts

- Vehicle availability is derived from vehicle status and relevant active/reserved rentals; it is not persisted independently.
- Customer rental history is derived from `Rental` relations.
- Rental outstanding balance is derived from `Rental.total_amount` less valid, non-deleted `Payment.amount` records.
- Revenue and expense period reporting use payment and expense dates. Maintenance financial reporting uses completed `Maintenance.cost` separately from non-maintenance `Expense.amount`.
- Maintenance and task upcoming/overdue states are date-derived presentation/query concepts, not enum values.
- Contract fields are historical snapshots, not live joins to mutable customer/vehicle facts.

## 9. Deferred or Future Models

### 9.1 Notifications and Reminder Delivery

No `Notification` model, notification enum, scheduler, background reminder job, or delivery channel is implemented. Product reminder requirements remain future work; task completion and maintenance schedules do not imply notification delivery.

### 9.2 Online Payment Processing

Payments are manual/recorded receipts only. Whish, QR payments, gateways, checkout, webhooks, refunds, chargebacks, payment intents, and online transaction state are explicitly outside this model.

### 9.3 SaaS Billing and Subscriptions

Subscription plans, billing accounts, invoices, pricing, and payment collection for the SaaS are deferred. Organization lifecycle status is not a subscription model.

### 9.4 Platform Administration UI

The `PLATFORM_OWNER` role, organization lifecycle endpoint, and audit capability are implemented backend concepts. A platform-admin dashboard UI is deferred.

### 9.5 Future Product Modules

Reservations beyond the implemented rental lifecycle, vehicle sales, buyers, sales contracts, branches, inventory, customer self-service, accounting integration, advanced analytics, advanced recurrence, offline conflict workflow, and maintenance automation require separate approved design and implementation work.

## 10. Open Decisions

- Notification persistence, type/read-state model, generation policy, and delivery mechanism.
- SaaS billing/subscription domain model and its relationship to organization lifecycle.
- Complex task recurrence beyond interval plus unit and end condition, task associations, background scheduling, and reminder delivery.
- Automated maintenance schedule evaluation, maintenance creation, mileage updates, availability effects, and notification workflow.
- Future sales, reservations, branch, inventory, accounting, and customer-facing modules.

## 11. Implementation Contract

- Prisma definitions and migrations must match the currently implemented fields, enum values, FKs, unique constraints, indexes, defaults, and explicit check constraints above. Approved target fields remain pending until implemented.
- Repositories scope tenant-owned records by organization and preserve soft-delete filtering.
- Services own transactions and cross-record business rules, including tenant ownership, rental availability, invitation acceptance, password reset, implemented task succession, and lifecycle transitions. The approved target task recurrence rules apply when their implementation is completed.
- Validators enforce the documented required, format, enum, and range rules. Database constraints complement rather than replace service validation.
- APIs and tests preserve the implemented model and public contract; approved target fields and workflows must not be treated as implemented until their schema/API/application changes land.
- Changes to an implemented model, constraint, or rule require explicit architectural approval and corresponding schema/API documentation updates.
