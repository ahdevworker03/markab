# Milestone 5.6 — Backend & Database Correctness Remediation

## Purpose and sequencing

This plan remediates the seven accepted findings in [the backend correctness audit](./backend-correctness-audit.md). It treats the Node/Express/Prisma implementation as the production target and the audit as the evidence source. Correctness fixes come before structural cleanup. No reference implementation architecture is to be ported merely for parity.

The current API is feature-modular and layered (`routes → controllers → services → repositories → Prisma`). The plan preserves that boundary, adds transactions and domain checks where the audit demonstrated they are missing, and updates the OpenAPI source and generated packages only when an externally observable API result changes.

## Shared implementation rules

- Use `lib/api-spec/openapi.yaml` as contract source; regenerate `lib/api-zod` and `lib/api-client-react` after any contract change. Do not edit generated files manually.
- Use the existing transaction helper in `apps/api/src/database/transaction.ts`; use serializable transactions for multi-record lifecycle changes and retry only documented serialization conflicts.
- Keep tenant scoping as a regression requirement. The audit did not establish a tenant-isolation defect.
- Preserve soft-delete history. Do not hide corrupted data or convert unexpected storage failures into success.
- Do not add a platform-admin dashboard, subscriptions, or unrelated frontend work in this remediation milestone.
- Every step must leave the API typecheck, applicable tests, root lint, and `git diff --check` clean before proceeding.

## Step 23 — Customer Data Integrity

### Must Read

- BDA-007 and audit sections 6–10
- `apps/api/src/modules/customers/*`
- `lib/db/prisma/schema.prisma` and customer migrations
- customer schemas in `lib/api-spec/openapi.yaml`
- `lib/db/src/seed.ts`

### Objectives

Fix the confirmed `GET /api/customers` crash without concealing invalid customer licence data. The confirmed field is `Customer.license_expiry_date`, serialized as API `licenseExpiryDate` at `customer.service.ts:30`.

### Scope

- Inspect the actual offending active row(s), including raw PostgreSQL timestamp representation, customer ID, tenant, and insertion history if available.
- Define the supported business date range for licence expiry, then validate it at the API/application boundary and, if appropriate, at the database boundary.
- Repair or quarantine only confirmed invalid records through an approved, auditable migration or operational repair procedure.
- Make list/detail mapping return the selected explicit data-integrity outcome for any remaining invalid persisted value; do not null, substitute, silently omit, or swallow it.

### Deliverables

- Root-cause evidence: the exact persisted value and a classification of whether its insertion path is known or remains unknown.
- A documented supported date range and the selected database constraint/repair strategy.
- A mapper/data-integrity error path that cannot turn one invalid `Date` into an unhandled 500.
- Regression tests for list, detail, create, update, and tenant isolation.

### Acceptance Criteria

- Every active QA-tenant customer has a serializable `license_expiry_date` within the approved range.
- `GET /api/customers` and customer detail succeed for repaired valid data.
- A deliberately invalid persisted value produces the documented deliberate outcome and does not masquerade as valid customer data.
- Normal create/update rejects dates outside the approved range.

### Verification

- Run the Step 22 database baseline first.
- Run customer service and route tests, then the complete API suite.
- If the response/error semantics change, update `lib/api-spec/openapi.yaml`, run `pnpm --filter @workspace/api-spec codegen`, and then run API typecheck plus web typecheck/test/build.
- Run `pnpm lint` and `git diff --check`.

### Manual Testing

1. List customers in the affected tenant.
2. Open the formerly affected customer and verify the displayed expiry date.
3. Create and update a customer at the approved date boundaries.
4. Verify a second tenant cannot view or modify the first tenant’s customer.

### Stop Conditions

Do not choose the repair value, quarantine rule, or exact database constraint until database inspection identifies the persisted value and the product owner approves the legitimate business date range. The audit proves the crashing field, not the original insertion path.

### Report Requirements

Record affected row IDs, approved range, repair/quarantine action, migration status, API result, and the tests proving the failure cannot recur. Do not include customer PII beyond the minimum identifiers needed for the repair record.

## Step 24 — Rental Lifecycle Integrity

### Must Read

- BDA-001 and BDA-002
- `apps/api/src/modules/rentals/*`
- `apps/api/src/database/transaction.ts`
- rental, vehicle, and availability schemas in `lib/api-spec/openapi.yaml`
- `docs/product/02-business-requirements.md` sections 5, 6, and 16

### Objectives

Remediate rental PATCH invariant bypass and soft-delete vehicle-state drift as one lifecycle boundary. This prevents invalid amendments, double booking, and stranded vehicle status without changing unrelated rental behavior.

### Scope

- Route every rental PATCH through the same effective-value calculation and invariant checks used by creation/extension.
- Validate effective pickup/expected-return period, amounts, and allowed status changes.
- Check overlaps excluding the rental being amended.
- Define and implement an explicit deletion policy: reject deleting `ACTIVE` rentals; for an eligible `RESERVED` rental, soft-delete and release the vehicle atomically only when no other live rental requires it. Keep cancellation as the normal release action.
- Use serializable transactions for amendment/deletion and vehicle state synchronization.

### Deliverables

- A focused rental invariant helper or equivalent service-level boundary, shared only where it prevents duplicated lifecycle rules.
- Repository support for overlap checks that exclude the current rental within a transaction.
- Explicit conflict errors and OpenAPI responses if externally observable outcomes differ from the present contract.
- Service and route regression coverage, including concurrency/serialization-conflict behavior.

### Acceptance Criteria

- PATCH cannot create reversed/equal dates, invalid effective monetary values, or an overlap with a different live rental.
- PATCH cannot apply an unapproved transition to `RETURNED` or `CANCELLED` rentals.
- Soft-deleting an eligible reservation does not strand its vehicle as `RESERVED`.
- Deleting an `ACTIVE` rental returns a documented conflict and preserves the vehicle lifecycle.
- Tenant scoping holds for every read and write path.

### Verification

- Reset the test database and run rental unit/service/route tests, including concurrent conflicting amendment tests.
- Run the complete API suite, API typecheck, root lint, and `git diff --check`.
- Update OpenAPI and regenerate both client packages only if new `409` outcomes or response semantics are contractual; then run web typecheck/test/build.

### Manual Testing

1. Create a reservation and amend dates/amounts within valid limits.
2. Attempt an overlap amendment for the same vehicle and confirm a conflict.
3. Attempt reversed and equal pickup/return dates.
4. Delete an eligible reservation and verify vehicle availability returns.
5. Attempt to delete an active rental and confirm it is rejected; use cancellation/return and verify the correct release behavior.

### Stop Conditions

Stop for product clarification if the product requires hard deletion, deletion of active rentals, or a status transition that is not documented by current business rules. Do not infer these policies from the reference implementation.

### Report Requirements

Record the allowed transition matrix, delete policy, transaction boundaries, any OpenAPI change, race-condition test result, and two-tenant manual result.

## Step 25 — Maintenance Availability Integrity

### Must Read

- BDA-003
- `apps/api/src/modules/maintenance/*`
- rental availability and vehicle-status code/tests
- `lib/db/prisma/schema.prisma` vehicle and maintenance enums
- maintenance and vehicle schemas in `lib/api-spec/openapi.yaml`

### Objectives

Ensure maintenance lifecycle changes accurately control rental availability and do not overwrite an active rental state.

### Scope

- When maintenance enters `IN_PROGRESS`, atomically set the vehicle to `MAINTENANCE` only when the vehicle has no conflicting live rental.
- When maintenance completes or is deleted, restore vehicle availability only when no other in-progress maintenance or live rental blocks it.
- Define behavior for multiple maintenance records without allowing the first completion to restore the vehicle prematurely.
- Return a business conflict rather than force an invalid maintenance/rental combination.

### Deliverables

- A single transaction-owned availability decision for maintenance state and vehicle status.
- Repository queries needed to determine live rentals and other in-progress maintenance records under the transaction.
- Regression tests spanning maintenance, vehicle status, and rental availability.

### Acceptance Criteria

- An in-progress maintenance record makes the vehicle unavailable to new reservations.
- Completing the last blocking maintenance returns an otherwise free vehicle to its correct operational status.
- Completion/deletion does not make a vehicle available when another active maintenance record or live rental still blocks it.
- Cross-tenant maintenance actions cannot affect another tenant’s vehicle.

### Verification

- Run maintenance service/route tests and rental availability regression tests against a reset test DB.
- Run the complete API suite, API typecheck, root lint, and `git diff --check`.
- If new conflict responses are added to the public behavior, update OpenAPI, regenerate, and run web verification.

### Manual Testing

1. Start maintenance for an available vehicle and confirm it disappears from availability.
2. Attempt a reservation while it is in progress and confirm a conflict.
3. Complete maintenance and confirm availability returns only when no live rental blocks it.
4. Repeat with two maintenance records and with an active rental conflict.

### Stop Conditions

Stop if the product needs a distinct post-maintenance inspection status or a rule that allows maintenance during an active rental; neither should be invented in this fix.

### Report Requirements

Record the vehicle-status transition table, conflict policy, transaction tests, and manual availability results.

## Step 26 — Tenant Provisioning Integrity

### Must Read

- BDA-006
- `apps/api/src/modules/auth/*`
- `apps/api/src/database/transaction.ts`
- user/organization constraints in `lib/db/prisma/schema.prisma`
- registration contract in `lib/api-spec/openapi.yaml`
- authorization rules in `docs/architecture/07-authentication-and-authorization.md`

### Objectives

Make organization registration an atomic tenant-provisioning boundary: either both organization and first `OWNER` exist, or neither does.

### Scope

- Put organization and owner creation in one Prisma transaction.
- Preserve globally unique email behavior and map duplicate email races consistently to the existing contract error.
- Issue access/refresh tokens only after a successful transaction commit.
- Do not introduce platform-owner provisioning, dashboard routes, or subscription logic.

### Deliverables

- A transaction-based registration flow using the project transaction helper where suitable.
- Deterministic duplicate-email/race error handling.
- Auth route/service tests for success, duplicate/concurrent registration, rollback/orphan prevention, and token issuance sequencing.

### Acceptance Criteria

- Successful registration creates exactly one organization and one tenant `OWNER`.
- Any owner-create failure leaves no ownerless organization.
- Duplicate or concurrent registration does not create an extra tenant.
- No token is returned before the provisioning transaction commits.

### Verification

- Reset the test DB; run auth tests and the full API suite.
- Run API typecheck, root lint, and `git diff --check`.
- Keep OpenAPI unchanged unless the public error contract changes; if it does, regenerate clients and run web typecheck/test/build.

### Manual Testing

1. Register a new uniquely named test organization and verify owner login.
2. Repeat the same registration and verify a conflict without a second organization.
3. Inspect the created tenant/user pair through approved development tooling; clean test data only by approved test/reset workflow.

### Stop Conditions

Stop if registration must provision subscriptions, a platform owner, invitations, or external identity records. Those are not part of this atomicity repair.

### Report Requirements

Record transaction semantics, duplicate-email behavior, orphan count before/after the failure tests, token sequencing evidence, and the final authorization scope.

## Step 27 — Media and Signed Contract Reliability

### Must Read

- BDA-005
- `apps/api/src/modules/media/*`
- `apps/api/src/modules/contracts/*`
- `apps/api/src/storage/*` and global error middleware
- media/contract download and upload paths in `lib/api-spec/openapi.yaml`

### Objectives

Restore database/storage consistency for vehicle documents, customer documents, and signed contracts, and translate missing stored objects into stable domain responses.

### Scope

- Map a missing local storage object (`ENOENT`, and provider-equivalent absence) to a stable `404 FILE_NOT_FOUND` domain error without filesystem detail leakage.
- Preserve unexpected storage failures as internal errors.
- After an upload succeeds but metadata persistence fails, compensate by deleting the stored object; record/log cleanup failure without hiding the original persistence error.
- Apply the same behavior to customer documents, vehicle documents, and signed contract uploads/downloads.
- Retain existing path-containment and file validation protections.

### Deliverables

- A narrowly scoped storage-error boundary, not duplicated filesystem-error handling in every controller.
- Compensating cleanup around metadata writes in media and contract services.
- Route/service tests for all three document domains and the unexpected-error path.

### Acceptance Criteria

- A database document pointing at an absent object returns `404 FILE_NOT_FOUND`, not `500`.
- A failed metadata create attempts storage cleanup and leaves no accessible orphan when cleanup succeeds.
- Unexpected retrieve/store/delete failures still surface as internal failures and are observable to operators.
- Tenant scoping and file type/size checks remain unchanged.

### Verification

- Run media/contract route and service tests using isolated temporary storage and a reset test DB.
- Run the full API suite, API typecheck, root lint, and `git diff --check`.
- Update OpenAPI and regenerate clients if `FILE_NOT_FOUND` is newly documented; then run web typecheck/test/build.

### Manual Testing

1. Upload and download a customer document and vehicle document.
2. Upload and download a signed contract.
3. In a controlled local test fixture only, remove a stored object and verify a 404 response.
4. Simulate metadata persistence failure in an automated test and inspect that compensation is attempted.

### Stop Conditions

Stop if production storage-provider semantics do not distinguish absence from permission/network failure. Define provider error normalization before changing HTTP behavior.

### Report Requirements

Record response codes, storage-error mapping, compensation outcome, cleanup-failure observability, and all document-domain test results.

### Objectives

Allow a deleted contract to be corrected and regenerated without losing an auditable lifecycle or violating the one-active-contract rule.

### Scope

- Make active lookup explicitly exclude `deleted_at` where appropriate.

- Protect concurrent generation so two active contracts cannot result.

### Deliverables

- Active-contract repository lookup behavior consistent with that policy.
- If needed, a reviewed Prisma migration and migration test; otherwise a statement explaining why the existing unique constraint remains valid.

### Acceptance Criteria

- Generate → delete → regenerate produces one usable active contract under the approved policy.
- Deleted contract reads remain not found.
- Tenant isolation and signed-document ownership remain intact.
- Concurrent generation cannot produce two active contracts or a misleading success response.

### Verification

- Apply/reset migrations in the dedicated test database when schema changes are selected.
- Run contract tests, the full API suite, API typecheck, root lint, and `git diff --check`.
- If endpoint behavior/error responses change, update OpenAPI, regenerate, and run web typecheck/test/build.

### Manual Testing

### Stop Conditions

### Objectives

### Deliverables

### Verification

## Risks and controls

| Risk                                                                                                   | Control                                                                                                          |
| ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| Repairing the customer date without knowing its value/source destroys evidence or valid business data. | Inspect first, record the row and approved range, then use an auditable repair/quarantine action.                |
| Rental/maintenance state changes race under concurrent requests.                                       | Use serializable transactions, transaction-scoped overlap/blocker queries, and concurrency tests.                |
| A fix changes public error behavior without consumers learning it.                                     | Update OpenAPI first when behavior is contractual, regenerate, and run web verification.                         |
| Storage compensation masks the original error or deletes an unrelated object.                          | Use the exact newly-created storage key, preserve/log the original failure, and test cleanup failure separately. |
| Contract change weakens history or allows two active rows.                                             | Select lifecycle policy before implementation, preserve active uniqueness, and test concurrent generation.       |
| Refactoring broadens scope and delays customer QA.                                                     | Place it after correctness gates; split only to reduce a demonstrated maintainability/correctness risk.          |
| Test reset touches development data.                                                                   | Use the explicit `vehicle_rental_test` URL only; never run reset against `vehicle_rental`.                       |

## Product decisions and resolutions

1. **Customer licence date range and remediation:** resolved with the approved `1900-01-01` through `2100-12-31` range and repair of the confirmed invalid row; quarantine was not used.
2. **Contract regeneration:** resolved with restore/replace of the existing unsigned soft-deleted contract row; signed-document regeneration returns a business conflict.
3. **Rental deletion policy edge cases:** resolved by rejecting `ACTIVE` rental deletion and atomically releasing eligible reserved rentals.
4. **Maintenance/rental collision policy:** resolved by rejecting maintenance start when a live rental conflicts and preserving blocking vehicle state.
5. **Payment overpayment:** resolved with Version 2 policy: partial and exact-payoff payments succeed; payments exceeding the current outstanding balance return `PAYMENT_EXCEEDS_OUTSTANDING_BALANCE`.
6. **Platform administration:** remains a Milestone 6 feature and was not included in this milestone.
