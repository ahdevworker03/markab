## Goal

Upgrade `apps/web` into a polished, responsive, Arabic-first SaaS product before Milestone 6. The work improves tenant-facing UI/UX, frontend structure, generated API-client integration, and missing screens for approved backend capabilities while preserving established business behavior and contracts.

The implementation baseline is:

- `docs/architecture/12-ui-design-system.md`
- `docs/audits/frontend-work/ui-audit-result.md`

The current `apps/web` source is the practical frontend reference. `docs/architecture/03-frontend-architecture.md` describes the older mock prototype and must not override current source or the updated audit/design-system documents.

## Rule

**Rule:** No step may be skipped. Every step must be:

1. Implemented.
2. Reviewed by the AI agent.
3. Reviewed by the product owner.
4. Tested.
5. Committed.

Only after all acceptance criteria are satisfied may the next step begin.

- Existing backend behavior and API contracts must be preserved unless a verified frontend integration bug requires a narrowly scoped fix.
- Shared layout and design-system work must precede screen rebuild work.
- Every implementation phase requires automated checks and responsive/manual review.
- Do not introduce Version 2-excluded features.

## Scope

- Practical feature-based frontend structure and shared infrastructure cleanup.
- Responsive app shell, navigation, dashboard, core business, operations, insights, auth, account, and organization UI.
- API-consistent loading, unavailable, zero, empty, error, submitting, and permission states.
- Existing API-backed support for document expiry, recurring tasks, maintenance schedules, invitations, password reset, organization profile, and organization lifecycle status.
- Arabic RTL, mixed-direction value, accessibility, and responsive quality at 375px, 768px, 1024px, 1440px, and 1920px.

## Non-Goals

- Backend/database correctness remediation, new backend features, or API-contract changes unless a verified frontend integration gap requires a narrowly scoped fix.
- Production deployment, offline synchronization, real password-reset delivery, secure `PLATFORM_OWNER` bootstrap/runbook, performance/security hardening, or Milestone 6 documentation work.
- Full Platform Admin Dashboard, billing/subscriptions, Whish/QR payments, notification delivery, background schedulers, maintenance automation, vehicle sales, customer portal, online reservations, accounting integrations, support CRM, or tenant impersonation.
- A platform-owner route/entry point may be reserved only as a boundary for Milestone 6. Tenant-facing navigation must not expose platform controls.

## Current Baseline

- `App.tsx` uses Wouter, `AppShell`, `ProtectedRoute`, `QueryProvider`, and `AuthProvider`; only `/login` is currently public.
- Existing pages cover dashboard, vehicles, customers, rentals, maintenance, expenses, tasks, analytics, and reports, with many add/edit/detail routes.
- The application has shared layout, domain, and shadcn-style UI components plus generated TanStack Query client hooks.
- Legacy hooks under `features/vehicles`, `features/customers`, and `features/rentals` still read local data, while newer screens use `@workspace/api-client-react`. This mixed source is a P0 frontend truthfulness risk.
- Registration, password reset, invitation acceptance, organization profile, maintenance schedule, and organization lifecycle APIs are generated but not fully represented as frontend routes/workflows.

## Step 41 — Feature-Based Frontend Structure Plan

### Must Read

- Step 40 outputs.
- `apps/web/src/App.tsx`, `features/`, `components/`, `components/layout/`, `components/ui/`, `providers/`, `hooks/`, `lib/`, `data/`, and generated client usage.

### Objectives

Define a practical migration plan from the current flat/mixed frontend structure to a feature-based architecture without rewriting the application.

The plan must classify current frontend files by ownership and define where each file should live after the refactor.

**Scope:** Inspect the current frontend structure and classify relevant files into:

- app-owned
- feature-owned
- shared UI
- shared layout/infrastructure
- shared utilities/hooks
- transitional or obsolete

The plan must explicitly review these crowded areas:

- The pre-migration `apps/web/src/pages` directory and its post-migration feature owners.
- `apps/web/src/components`
- `apps/web/src/components/layout`
- `apps/web/src/components/ui`
- `apps/web/src/lib`
- `apps/web/src/hooks`
- `apps/web/src/providers`
- `apps/web/src/features`
- `apps/web/src/data`

Domain-specific pages, components, hooks, selectors, schemas, helpers, and API adapters should move under their owning feature where appropriate.

Shared shadcn-style primitives and genuinely reusable UI components should remain shared and must not be duplicated across features.

Shared layout code may be grouped by responsibility, for example:

```text
components/
  layout/
    shell/
    navigation/
    page/
```

The target frontend direction should be approximately:

```text
src/
  app/
    routes/
    providers/
    App.tsx

  features/
    auth/
    dashboard/
    vehicles/
    customers/
    rentals/
    maintenance/
    expenses/
    tasks/
    analytics/
    reports/
    organization/

  components/
    layout/
    ui/

  hooks/
  lib/
  data/
```

The exact structure must be based on repository inspection rather than forcing empty or unnecessary folders.

For every route-level page and domain-specific component/helper, define its intended target owner.

Also inspect file size and responsibility boundaries.

Files larger than roughly **300-400 lines** should be reviewed for splitting when they contain multiple responsibilities.

Reduce oversized files by extracting cohesive concerns such as:

- page sections
- domain components
- form schemas
- form sections
- hooks
- selectors
- helpers
- API adapters
- configuration
- route definitions

Do not split files only to satisfy a line-count target. A large file may remain intact when it represents one cohesive responsibility and splitting it would make the code harder to understand.

When splitting an oversized file:

- preserve existing behavior
- preserve public component/hook contracts where practical
- avoid circular dependencies
- avoid creating tiny one-use files without a clear responsibility
- keep related code close to its owning feature
- update tests/imports as part of the later migration step
- do not change business logic merely to reduce file size

The plan must also define:

- import boundaries between `app`, `features`, and shared code
- migration order
- local/mock data retirement order
- which top-level folders should disappear, shrink, or remain shared
- which oversized files need decomposition during the migration
- which files should remain unchanged because they are already correctly owned

**Excluded:** Moving files, changing imports, splitting files, visual redesign, changing routes, replacing frameworks/libraries, changing API contracts, or changing business behavior in this planning step.

### Deliverables

- Exact target frontend folder structure based on current repository ownership.
- File ownership/migration map for current pages, components, layout, UI, hooks, providers, lib, and data.
- List of domain-specific files that should move into features.
- List of shared files that should remain shared.
- List of oversized files above roughly 300-400 lines that should be decomposed, with the intended responsibility split.
- Approved migration order.
- Import-boundary rules.
- Explicit local/mock-data retirement order.

### Acceptance Criteria

- Every current route-level page has an explicit target owner.
- Every domain-specific component/helper reviewed has an explicit feature or shared owner.
- Shared shadcn/UI primitives remain shared rather than being duplicated inside features.
- `pages/`, `components/layout/`, `components/ui/`, `lib/`, and other crowded folders are evaluated individually instead of being reorganized blindly.
- The plan identifies which crowded folders will disappear, shrink, or be reorganized after migration.
- Oversized files above roughly 300-400 lines are identified and only scheduled for splitting where multiple responsibilities justify it.
- No file is split purely to meet an arbitrary line-count requirement.
- The proposed structure preserves Wouter, Tailwind, existing shadcn-style primitives, generated API hooks, current routes, and existing business behavior.
- The migration plan avoids circular dependencies and unnecessary abstractions.
- Dashboard, vehicle, customer, and rental screens have a clear path away from mixed local/API data sources.

### Testing Requirements

- **Automated tests:** None required while this step remains a structure plan; identify colocated tests that must move with their owning feature in Step 42.
- **Static/regression verification:** Review the ownership map against the current source tree, import boundaries, routes, and existing test locations; run `git diff --check`.
- **Manual verification:** Product owner confirms the plan preserves current workflows and does not introduce empty abstractions or unintended route/UI changes.

### Verification

- Documentation review and repository ownership review against the current `apps/web/src` tree.
- AI/product-owner approval.
- `git diff --check`.

### Step Result

#### Target Structure

The migration remains incremental. `apps/web/src/App.tsx` stays the Wouter composition root, and it imports each feature's public page entry point. No empty folders are created without an owning responsibility.

```text
src/
  app/          route composition and application-level providers
  features/     domain pages, components, API adapters, selectors, and tests
  components/   shared layout and application-neutral UI only
  hooks/        shared UI/general hooks
  lib/          route-independent utilities, formatting, labels, and API helpers
  data/         transitional local data until its remaining consumers are migrated
```

#### Route Ownership Map

| Routes          | Target owner                     |
| --------------- | -------------------------------- |
| `/login`        | `features/auth`                  |
| `/`             | `features/dashboard`             |
| `/vehicles*`    | `features/vehicles`              |
| `/customers*`   | `features/customers`             |
| `/rentals*`     | `features/rentals`               |
| `/maintenance*` | `features/maintenance`           |
| `/expenses*`    | `features/expenses`              |
| `/tasks*`       | `features/tasks`                 |
| `/analytics`    | new `features/analytics`         |
| `/reports`      | `features/reports`               |
| unmatched route | application-level not-found page |

The existing protected full-screen create flows remain outside `AppShell`; route ownership changes must not alter their protection or focused-flow behavior.

#### Ownership and Migration Map

- Move `components/{vehicles,customers,rentals,expenses,maintenance,tasks,dashboard}` into the matching feature's `components/` directory.
- Move domain-aware files currently under `components/ui` into the owning feature: vehicle/customer/rental/expense/maintenance/task cards, `PaymentSection`, `ContractSection`, media/document components, `VehicleAvailabilitySection`, `MaintenanceHistorySection`, and `PeriodSelector`.
- Keep shared `components/layout`, providers, generic hooks, API configuration/error/token/format utilities, shadcn-style primitives, and application-neutral composites such as `FeedbackState`, `FormField`, `FormSection`, `SearchBar`, `FilterChips`, `SectionCard`, `SectionHeader`, `InfoRow`, and `StatusBadge` shared.
- Move page implementations from `pages/` into their owning feature only during Step 42. `App.tsx` remains the route composition boundary.

#### Local Data Retirement Order

1. Replace local vehicle and customer hooks with feature-owned generated-client query adapters; move selectors and consumers to generated response types.
2. Consolidate local rental hooks and API-backed rental availability/relationship hooks into feature-owned generated-client rental adapters.
3. Migrate dashboard and analytics after all their vehicle, customer, and rental inputs have one authoritative API source; remove fixed mock-date assumptions only then.
4. Remove `data/`, `lib/mock-date.ts`, and related legacy fixtures/tests only after all runtime consumers and selector tests use generated response fixtures/types.

#### Oversized Files

| File                                                                                                                          | Planned action                                                                                         |
| ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `features/analytics/pages/AnalyticsPage.tsx`                                                                                  | Keep page orchestration; extract feature selectors and chart/metric sections into `features/analytics` |
| `features/dashboard/pages/DashboardPage.tsx`                                                                                  | Extract derivation and alert/activity/fleet/financial sections into `features/dashboard`               |
| `features/reports/pages/ReportsPage.tsx`                                                                                      | Extract report export/print helpers and report metric/row components into `features/reports`           |
| `features/contracts/components/ContractSection.tsx`                                                                           | Split lifecycle and signed-document concerns only if further maintenance requires it                   |
| `features/rentals/pages/RentalDetailPage.tsx`                                                                                 | No mandatory split because it remains one detail composition                                           |
| `components/ui/sidebar.tsx`, `components/ui/chart.tsx`, `features/reports/selectors.ts`, `features/reports/selectors.test.ts` | Retain current ownership; each is cohesive shared/feature logic rather than a forced line-count split  |

#### Import Boundaries

1. `App.tsx` owns routes and global provider composition. Features never import `App.tsx` or another feature's private page/component/hook files.
2. Feature code may import its own internals, shared `components/ui`, shared layout, `hooks`, `lib`, providers, and generated client packages.
3. Cross-feature composition uses a public feature entry point. Parent pages compose related public feature components; related features never import the parent page.
4. Generated API calls belong in feature data hooks/adapters, not shared UI components or route pages.
5. Shared UI, layout, hooks, utilities, and providers do not import feature pages or domain components.

### Completion Gate

- AI ownership review is complete.
- No frontend code, route, API-contract, or backend change was made.
- Product-owner review, the required documentation test/review evidence, and the required commit remain pending before Step 41 can be marked complete.
