This plan completes only the approved Version 2 schema and backend capabilities. Milestone 5.6 correctness fixes remain the baseline; Milestone 6 features are excluded.

## Shared rules

- Prisma/PostgreSQL remains persistence truth; use UUIDs, tenant foreign keys, and intentional migrations.
- Schema migrations precede dependent service/controller/API work. Inspect existing data before constraints or backfills.
- `PLATFORM_OWNER`, `OWNER`, and `EMPLOYEE` are the only roles. Never reintroduce `MANAGER` or `CLIENT`.
- `lib/api-spec/openapi.yaml` is contract truth; regenerate clients after API changes.
- Keep repository → service → controller → route layering and avoid unrelated refactors.

## Step 31 — Scope, Baseline, and Migration Inventory

### Purpose
Establish an evidence-based baseline and migration order without changing state.

### Must Read

Product vision, requirements, flows, domain model; architecture principles/backend/database/API/auth/domain-specification docs; current modules for organizations, auth/users, tasks, maintenance, media, contracts; `lib/db/prisma/schema.prisma`, all migrations, and the completed 5.6 report.

### Scope and deliverables

Inventory models, routes, role checks, soft-delete and tenant boundaries; identify rows requiring backfill; verify the actual 5.6/5.7 filenames and correct stale references only after path verification; publish dependency order for Steps 32–40.

### Acceptance and verification

No code/schema/migration/OpenAPI changes. Run read-only status checks, API typecheck/tests, root lint, and `git diff --check`. Record deferred work and risks.

## Step 32 — Organization Lifecycle and Company Profile

Add `OrganizationStatus` (`TRIAL`, `ACTIVE`, `SUSPENDED`, `CANCELLED`) with new registrations defaulting to `TRIAL`. Add only proven explicit profile fields: existing display `name`, plus `legal_name`, `phone`, `email`, `address`, and `contract_footer_text` where current contract/report consumers require them; do not add speculative tax, logo, plan, or billing fields. Add nullable transition timestamps only if needed for state history.

Add a narrow PLATFORM_OWNER-only lifecycle-management API. OWNER/EMPLOYEE cannot change status. Shared tenant-operational middleware permits TRIAL/ACTIVE and rejects SUSPENDED/CANCELLED on business routes with a deliberate error while leaving authentication, `/auth/me`, account-status visibility, and platform reactivation flows available. Backfill existing organizations deliberately before enforcing defaults. Update validation/OpenAPI/generated clients and test registration, profile, transitions, authorization, isolation, and blocked business access. Stop if route classification cannot preserve account-status access without a product decision.

## Step 33 — Narrow Platform/Security Audit Log

Add append-oriented `AuditLog`: optional organization and actor, action, target type/id, optional structured metadata, timestamp, and useful indexes. Provide a small transactional helper; do not implement event sourcing or log every CRUD operation. Record lifecycle changes, invitation create/accept, password-reset completion, role/account administration, and justified destructive/platform actions without secrets or token material. Test transaction coupling, attribution, retention, and tenant/platform visibility; no public audit UI is required.

## Step 34 — Document Expiry and Ownership Integrity

Add nullable business-date `Document.expiry_date` (`@db.Date`) for `REGISTRATION`, `INSURANCE`, and `OTHER`; expose date-only values and validate supported dates. Add a validated metadata update endpoint because the current API has upload/read but no update path. No reminder scheduler or notification delivery.

Before migration, inspect and repair ambiguous rows. Enforce exactly one explicit owner across the current model (`vehicle_id`, `customer_id`, or `contract_id`), preserving signed-contract documents while applying Vehicle XOR Customer semantics to vehicle/customer rows; do not introduce polymorphic ownership. Add a PostgreSQL check constraint and tests for valid/invalid combinations, date boundaries, update/list/detail, downloads, and tenant isolation. Stop rather than guessing on unresolved ownership.

## Step 35 — Employee Invitations

Add organization-scoped invitation records with fixed role `EMPLOYEE`, hashed random token, expiry, single-use/accepted timestamp, creator, and timestamps. Define one pending invitation per organization/email; resend invalidates the prior token. Add OWNER-protected creation and token-accept/set-password endpoints; no arbitrary roles, MANAGER, PLATFORM_OWNER invitations, email-verification subsystem, or invitation analytics. Use a minimal delivery adapter/test sink. Test expiry, replay, duplicates, password setup, isolation, audit logging, and transaction behavior; update OpenAPI/generated clients.

## Step 36 — Password Recovery

Add secure hashed, expiring, single-use reset tokens. Define generic non-enumerating request and confirm endpoints, password validation/hashing, atomic consumption/invalidation, and session invalidation consistent with existing auth. Audit completion. Use a small delivery abstraction without exposing raw tokens in production; no MFA/OAuth redesign. Test unknown, expired, reused, invalid, concurrent tokens and post-reset login; update contracts and clients.

## Step 37 — Recurring Tasks

Add `recurrence_type` (`NONE`, `DAILY`, `WEEKLY`, `MONTHLY`) and a self-reference identifying the predecessor/series, with at most one child occurrence per completed occurrence. Completion atomically creates the next `PENDING` task from the completed due date (daily/week/month with defined month-end clamping), preserving history and tenant isolation. Do not add schedulers, cron, timezone engines, notifications, or arbitrary associations. Test rollback, retries/concurrency, deletion, all intervals, and API/client compatibility.

## Step 38 — Recurring Maintenance Scheduling

Add an organization/vehicle schedule model with maintenance type, `schedule_type` (`DATE`, `MILEAGE`, `DATE_OR_MILEAGE`), nullable date/mileage intervals and next-due values, active flag, and timestamps. Validate the selected basis and use business dates. Add authorized CRUD only; do not generate Maintenance records, run jobs, send notifications, or add complex mileage automation. Test migration, validation, multiple schedules, activation, isolation, and interaction with existing availability rules; manually confirm schedules do not create records unexpectedly.

## Step 39 — Integrity Review and Deferred Decisions Register

Review new foreign keys, indexes, checks, nullable fields, soft-delete filters, audit attribution, backfills, and rollback procedures. Confirm no MANAGER/CLIENT in roles or public contracts. Record deferred SaaS plans/pricing/subscription billing/metering, Whish/QR payments, notifications/background reminders, advanced recurrence, maintenance automation, platform-admin dashboard UI (Milestone 6), contract version history, branches, portals, reservations, vehicle sales, and accounting integrations. Run clean migration/reset and Prisma/API/contract checks; do not alter unrelated behavior.

## Step 40 — Full Regression and Milestone Readiness

Run migration-from-empty verification, backend typecheck/tests, lint, diff check, API smoke tests, and tenant-isolation checks. If contracts changed, run web typecheck/test/build. Manually verify registration/TRIAL, suspension/cancellation, profile, invitations, reset, documents, recurring tasks, maintenance schedules, contracts, rentals, payments, and reports. Use only the dedicated test database for destructive reset.

**Ready for manual customer QA** means migrations and critical tests pass, smoke workflows and isolation/security invariants are verified, and no known tenant or financial-data corruption blocker remains. **Ready for Milestone 6** additionally means generated contracts are current and all deferred decisions are recorded without building the dashboard.

## Risks and stop conditions

- Ambiguous existing document owners must be resolved before the check constraint.
- Lifecycle middleware must not block `/auth/me` or platform account-status operations.
- Never ship reset/invitation delivery that exposes raw tokens.
- Stop if recurrence or maintenance requirements expand into timezone, scheduler, notification, or automation semantics.
- Stop for approval if a required profile field lacks an identified contract/report consumer. The current contract-owned `Document` rows are a known repository contradiction; Step 34 uses the three-owner check above to preserve them and must verify this interpretation before migration.

## Deferred decisions

The following decisions are intentionally deferred and are not implied by the
Milestone 5.7 schema/API work:

- SaaS plans, pricing, usage metering, and automated subscription billing.
- Whish API integration, QR-code online payments, gateway credentials,
  webhooks, refunds, and chargebacks. The existing recorded-payment model
  remains unchanged.
- Notification delivery and all background reminder processing for documents,
  tasks, and maintenance schedules.
- Advanced recurrence rules, cron syntax, timezone recurrence engines, yearly
  or custom task intervals, and automated maintenance-record generation.
- The platform-admin dashboard UI, which belongs to Milestone 6; the current
  `PLATFORM_OWNER` lifecycle API is authorization groundwork only.
- Contract version history, branches, customer portals, reservations, vehicle
  sales, and accounting integrations.

## Migration integrity and rollback boundary

Milestone 5.7 migrations are append-only Prisma history. The lifecycle
backfill and document-owner preflight are intentional data-integrity steps;
future production deployment must take a verified backup before applying them.
There are no destructive down migrations. If a deployed migration needs to be
corrected, use a reviewed forward migration rather than editing migration
history or manually changing production rows. A clean rebuild is permitted
only for the dedicated `vehicle_rental_test` database after explicit approval.
