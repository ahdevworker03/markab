# **Milestone 5.7 — Database Model Completion & Business Schema Alignment**

## **Purpose and sequencing**

This milestone aligns the database schema with the product’s business model after the immediate backend correctness work in Milestone 5.6.

Milestone 5.6 fixes confirmed backend/database correctness defects. Milestone 5.7 addresses **schema gaps** that are required by the product vision and business requirements but are not clearly covered by Milestone 5.6 or Milestone 6.

The product vision defines the platform as a centralized SaaS system for vehicle rental businesses, focused on simple daily workflows, reliability, maintainability, and avoiding unnecessary complexity.

The business requirements explicitly include organization/company information, employee access management, document expiration reminders, recurring maintenance, recurring tasks, and reminders.

This milestone should not become a broad redesign. It should improve the database model where the current schema is clearly weaker than the approved business requirements.

---

## **Out of scope**

Do **not** include the following in this milestone:

- Milestone 5.6 correctness defects.
- Offline synchronization implementation.
- Performance optimization.
- Security hardening.
- Deployment.
- Feature-based frontend refactor.
- Platform admin dashboard UI.
- Online payment integration.
- Final SaaS pricing plans.
- Automated billing.
- Vehicle sales implementation.
- Customer portal.
- Online reservations.
- Accounting integrations.
- Branch management implementation.

---

## **Important product decision**

Final subscription pricing is **not** decided now.

The current business decision is:

```text id="u9rpk4"
Give selected business owners a one-month pilot/testing period.
Use the pilot to understand real usage, storage cost, support effort, bugs, and business value.
Decide final plans/pricing after the pilot.
```

Therefore, this milestone may model tenant lifecycle/access status, but it must **not** lock pricing plans, plan limits, or online payment assumptions.

---

## **Shared implementation rules**

- Preserve the existing Prisma/PostgreSQL stack.
- Keep the current multi-tenant model centered on `Organization`.
- Every new business table must include `organization_id` unless it is clearly platform-owned.
- Use UUID primary keys.
- Use soft delete where the record has business or audit value.
- Add migrations intentionally; avoid unnecessary schema churn.
- Update `lib/api-spec/openapi.yaml` only when API behavior changes.
- Regenerate generated clients only after OpenAPI changes.
- Keep backend implementation layered: repository → service → controller → routes.
- Add tests for every schema/API behavior change.
- Do not build UI unless the step explicitly requires minimum frontend integration.
- Prefer simple models that support the current product, not speculative enterprise features.
