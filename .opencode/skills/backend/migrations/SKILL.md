# Migrations

## Purpose

This skill guides the agent in managing database schema changes using Prisma Migrate in a PostgreSQL environment. It covers the end-to-end migration workflow, from schema modification to production deployment, including conflict resolution, zero-downtime strategies, and rollback procedures. The goal is to safely and predictably evolve the database schema while maintaining data integrity and minimal downtime.

---

## When to Load

- User is modifying the Prisma schema or adding new models/fields.
- User mentions: `migration`, `prisma migrate`, `prisma db push`, `migrate diff`, `migrate reset`, `migrate deploy`, `migration file`, `schema drift`, `baseline`, `squash`.
- User asks about deploying schema changes, rolling back migrations, or resolving migration conflicts.
- User is planning zero-downtime database updates.

- Frontend or React development.

## Core Principles

1. **Use Migrations for Schema Changes** – Always use `prisma migrate` for production schema changes. Use `prisma db push` only in development for fast prototyping.
2. **Migrations Must Be Version Controlled** – Migration files are part of the codebase. Commit them to the repository to ensure reproducibility.
3. **One Migration Per Logical Change** – Group related schema changes that should be deployed together into a single migration. Avoid mixing unrelated changes.
4. **Never Edit Migration Files Manually** – Migration files are generated by Prisma; editing them manually can lead to drift and errors. Use the generated SQL as-is.
5. **Apply Migrations Safely in Production** – Use `prisma migrate deploy` to apply pending migrations. Never use `prisma migrate dev` in production.
6. **Plan for Downtime** – Some migrations require downtime (e.g., adding a NOT NULL column without a default). Plan and communicate these ahead of time.

## Decision Rules

### When to Migrate vs. Push

- **IF** you are in development and experimenting with schema changes, **THEN** use `prisma db push` to quickly update the database without generating migration files.
- **IF** you are preparing a migration for production, **THEN** use `prisma migrate dev` to generate a migration file.
- **IF** you are in production, **THEN** always use `prisma migrate deploy` to apply pending migrations.
- **IF** you need to reset the database in development, **THEN** use `prisma migrate reset` or `prisma db push --force-reset` as appropriate.

### Creating a Migration

1. **Modify the schema** – Update `schema.prisma` with the desired changes (new models, fields, enums, relations).
2. **Generate the migration** – Run `prisma migrate dev --name descriptive_name`.
3. **Review the generated SQL** – Check the migration file in `prisma/migrations/` to ensure it matches expectations.
4. **Apply in development** – The migration is automatically applied to the development database.
5. **Commit the migration** – Commit both the schema change and the migration file.

### Resolving Migration History Drift

- **IF** a migration file has been removed or the migration history has been altered, **THEN** use `prisma migrate diff` to generate a diff between the schema and the database.
- **IF** the database and schema are out of sync (shadow database issues), **THEN** consider resetting the migration history with `prisma migrate reset` (development only).
- **IF** in production and drift occurs, **THEN** manually apply SQL changes to reconcile the database to the expected state, then generate a new migration.

### Production Deployment

- **IF** deploying to staging or production, **THEN** use `prisma migrate deploy` to apply all pending migrations.
- **IF** you need to check which migrations have been applied, **THEN** use `prisma migrate status` or query the `_prisma_migrations` table.
- **IF** a migration fails in production, **THEN** roll back by applying a new migration that reverts the changes, or revert the deployment to a previous version.

### Zero-Downtime Migrations

- **IF** a migration requires adding a NOT NULL column, **THEN** follow the multi-step approach:
  1. Add the column with a default value or as nullable.
  2. Backfill the column in the application or via SQL.
  3. Alter the column to NOT NULL in a separate migration.
- **IF** a migration requires renaming a column or table, **THEN** use a three-step approach: create new column, copy data, drop old column.
- **IF** a migration requires dropping a column, **THEN** first remove usage in the application, then drop the column in a later deployment.
- **IF** a migration requires adding a foreign key, **THEN** ensure the referenced data exists before applying the constraint.

## Best Practices

1. **Use descriptive migration names** – Always provide a meaningful name with `--name` to identify the purpose (e.g., `add_user_avatar_field`).
2. **Keep migrations small and focused** – Each migration should represent one logical change to reduce risk and simplify rollback.
3. **Test migrations in development first** – Always test the migration locally before deploying to production.
4. **Review generated SQL** – Prisma generates SQL based on your schema; always review it for correctness and performance (e.g., indexes).
5. **Use `migrate diff` for custom migrations** – If you need fine-grained control, use `prisma migrate diff` to generate a SQL script, then apply it manually.
6. **Squash migrations periodically** – Over time, many small migrations accumulate. Squash them into a single migration to keep the migration history manageable.
7. **Apply migrations as part of the deployment pipeline** – Automate migration execution in CI/CD. Ensure the migration step runs before the application starts.
8. **Back up the database before production migrations** – Always have a recovery plan. Use database snapshots or point-in-time recovery.
9. **Monitor migration performance** – Large migrations can lock tables and cause downtime. Use `--create-only` to generate the SQL without applying, then apply it with custom timing.

## Anti-Patterns

| Anti-Pattern                                               | Why it is wrong                                                     | Correct approach                                                                |
| ---------------------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Manually editing migration files                           | Breaks the Prisma migration flow; can lead to drift.                | Let Prisma generate the migration; use `migrate diff` for custom SQL if needed. |
| Using `db push` in production                              | Bypasses migration history and version control.                     | Always use `migrate deploy` in production.                                      |
| Skipping migration review                                  | Errors in the generated SQL lead to downtime.                       | Review every migration file before deploying.                                   |
| Ignoring migration errors                                  | Leaves the database in an inconsistent state.                       | Resolve errors immediately; use rollback if necessary.                          |
| Not squashing migrations                                   | Migration history becomes very long; `migrate deploy` takes longer. | Periodically squash migrations.                                                 |
| Adding NOT NULL without default                            | Causes errors if existing rows have null values.                    | Add column with default, backfill, then add NOT NULL in separate migration.     |
| Dropping tables/columns without removing application usage | Application breaks when trying to access dropped fields.            | Remove usage in code first, then migrate.                                       |
| Applying migrations as part of app startup                 | Migration conflicts with app logic; risks data corruption.          | Apply migrations separately before starting the app.                            |

## Common Mistakes & Edge Cases

| Mistake                                                         | Symptom                                                             | Solution                                                                                                              |
| --------------------------------------------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `prisma migrate dev` fails due to shadow database               | Shadow database issues; can happen with custom databases.           | Use `--skip-generate` or set a custom shadow database URL.                                                            |
| Migration file conflict in CI/CD                                | Multiple developers generate conflicting migrations.                | Use `--create-only` to generate SQL without applying, then merge; use `migrate resolve` to resolve conflicts.         |
| `prisma migrate deploy` fails due to migration history mismatch | The `_prisma_migrations` table is out of sync.                      | Use `migrate diff` to understand the difference; apply custom SQL to sync.                                            |
| Schema changes require data transformation                      | Data migration is needed alongside schema changes.                  | Use `prisma migrate dev --create-only` to generate the SQL, then edit the migration file to add data transformations. |
| Renaming a field leads to data loss                             | The old column is dropped; data is lost.                            | Follow the three-step rename approach: add new column, copy data, drop old.                                           |
| Adding a unique constraint fails                                | Duplicate data exists; constraint cannot be applied.                | Remove duplicates before applying the migration.                                                                      |
| Squashing migrations loses history                              | The migration history is rewritten; may cause issues on production. | Only squash in development; use `prisma migrate diff` to generate a single migration file.                            |
